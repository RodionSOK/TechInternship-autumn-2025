# PR Reviewer Assignment Service

## Описание
Сервис для автоматического назначения ревьюеров на Pull Request'ы. Реализован на Go с использованием PostgreSQL.

## Запуск проекта

### Запуск через Docker Compose

1. Скопируйте `.env.example` в `.env`:

2. Запустите сервис:
```bash
make docker-up
```

Или напрямую:
```bash
docker-compose up -d
```

3. Сервис будет доступен на `http://localhost:8080`

### Остановка
```bash
make docker-down
```

## Конфигурация линтера

В проекте используется **golangci-lint** 

### Конфигурация

Конфигурация линтера находится в файле `.golangci.yml`:

**Включенные линтеры:**
- `errcheck` — проверяет, что все ошибки обработаны (не игнорируются)
- `govet` — встроенный анализатор Go, находит распространенные ошибки
- `staticcheck` — расширенный статический анализатор с дополнительными проверками
- `unused` — находит неиспользуемые константы, переменные, функции и типы
- `ineffassign` — находит неэффективные присваивания (переменная присваивается, но не используется)
- `misspell` — проверяет орфографию в комментариях и строках

**Настройки:**
- `timeout: 5m` — максимальное время выполнения линтера
- `tests: true` — проверка тестовых файлов
- `skip-dirs: migrations` — пропуск директории с миграциями
- `goimports.local-prefixes: pr-reviewer-service` — настройка группировки импортов

**Запуск:**
```bash
make lint
```

Или напрямую:
```bash
golangci-lint run ./...
```

## API Эндпоинты

- `POST /team/add` - Создать команду с участниками
- `GET /team/get?team_name=...` - Получить команду
- `POST /users/setIsActive` - Установить флаг активности пользователя
- `GET /users/getReview?user_id=...` - Получить PR'ы пользователя
- `POST /pullRequest/create` - Создать PR
- `POST /pullRequest/merge` - Пометить PR как MERGED
- `POST /pullRequest/reassign` - Переназначить ревьювера
- `GET /statistics` - Получить статистику (общее количество PR, статистика по пользователям)

**Пример ответа `/statistics`:**
```json
{
  "total_prs": 10,
  "open_prs": 3,
  "merged_prs": 7,
  "user_statistics": [
    {
      "user_id": "u1",
      "username": "Alice",
      "total_reviews": 5,
      "open_reviews": 2,
      "merged_reviews": 3
    },
    {
      "user_id": "u2",
      "username": "Bob",
      "total_reviews": 3,
      "open_reviews": 1,
      "merged_reviews": 2
    }
  ]
}
```

Полная спецификация API доступна в файле `openapi.yml`.

## Вопросы и принятые решения

### 1. Health эндпоинт
В OpenAPI есть тег `Health`, но эндпоинт не описан в спецификации. Решено не реализовывать, так как он не указан в требованиях.

### 2. Удаление команды (ON DELETE)
Использован `ON DELETE RESTRICT` для внешнего ключа `users.team_name`, чтобы предотвратить случайное удаление команды с пользователями.

### 3. Обработка неактивных ревьюверов

#### При переназначении:
- Неактивные ревьюверы автоматически заменяются активными из их команды. Если кандидата для замены нет, неактивный ревьювер удаляется из списка.
- Если после замены ревьюверов меньше 2, система пытается добавить еще одного активного ревьювера из команды автора.

**Пример:**
- Команда из 4 человек: `u1`, `u2`, `u3`, `u4`, где каждый участник `is_active = true`
- Меняем статус `u2`, `u3`: `is_active = false`
- Создаем PR, где `author_id: u1`
- У PR один ревьюер - `u4`
- Меняем статус `u3`: `is_active = true`
- Перевыбираем ревьюеров, указав единственно возможный `old_user_id: u4`
- Тогда ревьюерами станут `u3`, `u4`. Приоритет был сделан на то, чтобы в команде всегда было два ревьюера

#### При merge:
- Все неактивные ревьюверы удаляются перед изменением статуса PR.


### 4. Изменение статуса пользователя
Пользователь может менять свой статус (`isActive`) независимо от того, достаточно ли активных участников для ревью. Система автоматически обрабатывает последствия:
- При переназначении неактивные ревьюверы заменяются или удаляются
- При merge неактивные ревьюверы удаляются

### 5. Логика переназначения
- При переназначении используется команда **заменяемого ревьювера** (не автора), как указано в требованиях.
- Если в команде заменяемого ревьювера нет активных кандидатов, возвращается ошибка `NO_CANDIDATE`.
- После переназначения система проверяет всех ревьюверов и заменяет/удаляет неактивных.

### 6. Добавление ревьюверов при переназначении
Если после переназначения ревьюверов меньше 2, система пытается добавить еще одного активного ревьювера из команды автора, чтобы максимально приблизиться к 2 ревьюверам.

## E2E Тестирование

В проекте реализованы E2E (end-to-end) тесты.

### Структура E2E тестов

E2E тесты находятся в директории `tests/e2e/`:
- `helper.go` - вспомогательные функции для работы с HTTP клиентом
- `e2e_test.go` - тесты основных сценариев

### Запуск E2E тестов

E2E тесты используют отдельное тестовое окружение (отдельная БД и приложение на порту 8081):

```bash
make e2e-test
```

Эта команда:
1. Поднимает тестовое окружение (`docker-compose.e2e.yml`)
2. Ждет готовности сервисов
3. Запускает E2E тесты
4. Останавливает и удаляет тестовое окружение

### Покрываемые сценарии

E2E тесты проверяют следующие сценарии:
- Создание команды с участниками
- Создание PR с автоматическим назначением ревьюверов
- Получение команды
- Получение PR пользователя
- Переназначение ревьювера
- Изменение статуса активности пользователя
- Merge PR
- Проверка, что нельзя переназначить ревьювера после merge
- Получение статистики

### Тестовое окружение

E2E тесты используют отдельный `docker-compose.e2e.yml` с:
- Отдельной PostgreSQL базой данных (порт 5433)
- Отдельным экземпляром приложения (порт 8081)
- Автоматическим применением миграций
